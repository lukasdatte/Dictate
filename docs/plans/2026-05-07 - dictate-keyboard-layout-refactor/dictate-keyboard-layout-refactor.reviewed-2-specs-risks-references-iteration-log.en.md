### 2026-05-08 — Architecture-review pass: SOLID/DRY consolidation (F-1 to F-7)

After an architecture review in chat (focus: DRY, SOLID, long-term extensibility), seven discovered weaknesses were incorporated into the plan:

**F-1 (critical) — `PipelineStateManager` from God class to composition root.**
Earlier spec versions had designed the manager with five responsibilities
(state-mutation + pref-sync + FSM + recovery + JobExecutor-init). The substructure
into four helper classes is now explicit (Spec 1 §4.1):
- `DictateUiStateStore` (StateFlow-owner, pure data)
- `ViewModeFsm` (pure function: Triangle-FSM)
- `PipelinePrefMirror` (SP ↔ store mirroring)
- `PipelineRecovery` (DB replay)

The manager is now a composition root — orchestrates action methods + hardware,
delegates detail logic to the helper classes.

**F-2 (medium) — DIP via `PipelineSessionRepo` + `PipelineRunner` interfaces.**
Earlier constructor dependencies on `AppDatabase` (Room) and the static
`JobExecutor` object are abstracted via interfaces. Fully testable with
fakes without the Android stack (Spec 1 §4.2 + §13.3.11).

**F-3 (medium) — `DictatePipelineService` split.**
Notification building and action-PendingIntent routing are extracted into two dedicated
helper classes (Spec 1 §7.1):
- `PipelineNotificationCoordinator` (state → notification, throttled)
- `PipelineActionRouter` (PendingIntent → manager method)

The service class itself is now solely the process-lifecycle owner.

**F-4 (small) — `resolveAudioFocusIcon(enabled)` as a shared top-level helper.**
Eliminates the last drift source between the LayoutCatalog AUDIO_FOCUS slot and
EditBarController. Both sites not only read the same StateFlow but also
map via the same function (Spec 2 §8.5). Spec 2 Gap 1 RESOLVED.

**F-5 (small) — naming `PipelineState` → `DictateUiState`.**
The top-level data container is now called `DictateUiState`, eliminating the
confusing conflict with the sub-axis `PipelineUiState`. Renaming propagated through all
four plan files; `PipelineStateManager` (composition root for the
Pipeline-Service subsystem) keeps its name.

**F-6 (small) — `view.post {}` for GAP-7 (view-size-0 on first render).**
Instead of only a defensive `measuredWidth` fallback, `OverlayBackend.inflateAndAttach`
now triggers a `view.post { applyPosition(stateRef) }` hook after `dragHandler.attach`.
The callback fires after the first layout pass with then-correct view
dimensions and re-applies the position (Spec 3 §4.2). Spec 3 GAP-7 RESOLVED.

**F-7 (small) — shared slot-apply helper for both backends.**
`ImeViewBackend.applySlotProperties` and `OverlayBackend.applySlots` were duplicated as
separate methods with identical seven-line logic. Both now call
the top-level function `applySlotToView(slot, view, state, ctx)`
(Spec 2 §5.1, new file `keyboard/render/SlotRenderer.kt`). Spec 3 GAP-1
(`.foreground` vs `.icon` inconsistency) RESOLVED, because both backends run through
the same helper, which consistently uses `.icon`.

**Effect on the SOLID audit:** Spec 1 §13.3 is extended from 4 classes to 11 classes;
each new class has its own SRP/OCP/DIP justification.
**Effect on the DRY audit:** Spec 2 §13.4 has two new sections (F-4 + F-7);
two drift sources are structurally eliminated.
**Effect on extensibility:** A new slot property (e.g. `contentDescription`)
is added in exactly one place (`applySlotToView`); a new state axis
needs no manager reorganization; a fourth ViewMode (e.g. PIP) requires
only a `when` branch in `ViewModeFsm` and a new backend.

### 2026-05-09 / 2026-05-10 — Architecture consolidation pass 2: Modular Orchestrator (F-8 to F-11)

Following a more extensive architecture review, four further corrections were incorporated. They address the long-term scaling problem of centralized reducer/EffectRunner structures + the state inventory from Block 3.5 (15 axes, 8 missing pref-mirrors, new subsystem axes for BluetoothSco/Audio/Language/LivePrompt/Reprocess).

**F-8 (medium) — single dispatch via the `Action` sealed class.**
Earlier spec versions had the `LocalBinder` with ~25 typed forwarder methods,
parallel to an `Action` sealed class with identical variants — double
definition, DRY violation. Correction: the LocalBinder shrinks to
`state` + `dispatch(action: Action)` + 2 lifecycle hooks (View-Shown/Hidden,
which are internally fired as `ViewModeAction`). The Kotlin compiler enforces
exhaustivity in the reducer `when` — no action is forgotten. Spec 1 §5 adjusted.

**F-9 (medium) — library decision: no MVI framework + kotlinx.collections.immutable.**
After a library comparison (Orbit-MVI, MVIKotlin, Decompose, Mavericks, Tinder
StateMachine) decision: **adopt no MVI library**. Rationale:
- We are already at MVI with StateFlow + sealed Action + reducer + composition root;
  a library saves boilerplate but brings no architecture plus
- The plugin pattern (F-11) is not built into any library — we build it ourselves anyway
- IME-APK footprint is relevant — library adoption worsens it
- MVIKotlin bus factor 1 (Arkady Ivanov), Mavericks Android-only/Fragment-centric,
  Tinder StateMachine stagnant since 2021

**One** new library adoption: `kotlinx.collections.immutable` (~50 KB APK impact)
for true list immutability (`PersistentList<PendingSession>` instead of `List<PendingSession>`).
JetBrains-maintained, guaranteed longevity. Spec 1 §3 adjusted.

**F-10 (critical) — sub-state classes in DictateUiState (15 axes).**
The state inventory from Block 3.5 identified 15 state axes (3 hot-path FSMs,
7 subsystem axes, 8 pref-mirror axes). That would have led to a 30+-field data
class — the same SRP anti-pattern as F-1. Correction: hierarchical
**sub-state classes** per semantic axis (`AudioState`, `LayoutPrefs`,
`OverlayState`, `ResendState`, `LivePromptState`, `LanguageState`, `FeatureToggles`,
`ThemingState`, `InterruptionState`). Each sub-state class is immutable, is
managed by the respective module (F-11), has a clear responsibility.

Plus: the pref-mirror is extended by 9 additional UI-state-relevant prefs
(`RewordingEnabled`, `AutoFormattingEnabled`, `InstantOutput`, `Vibration`,
`Theme`, `AccentColor`, `OverlayCharacters`, `OutputSpeed`, `UseBluetoothMic`).
Spec 1 §3 + §4.5 adjusted.

**F-11 (critical) — Modular Orchestrator + DictateModule plugin pattern.**
Earlier designs had centralized reducer + EffectRunner with large `when`
blocks over all axes — does not scale: with 13 modules × 5-10 effects = 65-130
`when` branches in two files. Correction: **Modular Orchestrator pattern**,
inspired by the Excel-EKL module-augmentation pattern (TS `declare module`),
mapped in Kotlin via `sealed interface DictateModule` + `object` singletons.

- Each module encapsulates its **own sub-state + actions + reducer + side-effects +
  EffectHandler + cross-module observer** in one file
- `DictateOrchestrator` replaces the former `PipelineStateManager`; knows only
  the `DictateModule` interface, routes actions type-safe via `KClass<A>` lookup
- `DictateModuleRegistry` lists all 13 modules (12 active + 1 Phase-2) centrally
- Cross-module effects: three modes (own SideEffect, action cascade via
  `onCrossModuleStateChange`, atomic cross-axis reducer for rare cases)

Compile-time guarantees: the sealed interface enforces module completeness,
generics enforce type consistency per module, the KClass lookup guarantees unambiguous
action routing. Spec 1 §4 + §15 (NEW) adjusted.

**Effect on the file structure:** new directories `state/` and `state/modules/`
with 13 module files. Each module file is ~150-300 lines, coherent in itself.
Adding a new module = 1 new file + 4 small extensions (ModuleId,
Action.XxxAction, DictateUiState.subState, DictateModuleRegistry.all).

**What changed compared to the Block-3.7 design:**
- **`PipelineStateManager` → `DictateOrchestrator`** (renamed, leaner)
- **`ViewModeFsm` → `ViewModeModule`** (moves into the module system)
- **Central `EffectRunner` removed** — per module its own `runEffect`
- **Central `CrossAxisReducer` largely removed** — cross-module logic in the
  respective module via `onCrossModuleStateChange`. Atomic-cross-axis only for
  rare cases (e.g. Pipeline-Done affects Resend + LivePrompt + PendingSessions
  in one update — can optionally happen via a `Composed-Update` hook)

**Open questions still to be clarified in the implementation phase:**
1. **Reflection vs. manual registry**: currently a manual list in `DictateModuleRegistry.all`. Alternative: `DictateModule::class.sealedSubclasses.map { it.objectInstance }`. Trade-off: compile safety vs. R8/ProGuard robustness. Current recommendation: manual list with an init-check, reflection as an optional upgrade.
2. **KSP-based auto-discovery**: KSP (Kotlin Symbol Processing) could auto-register modules via an annotation. Overdimensioned today — documented as a Phase-2 option.
3. **Atomic cross-axis-update hook**: whether we need an optional `composeAtomic(prev, next, currentAction)` hook that allows a final atomic merge after normal reduce + cross-module cascade — solved today via dispatch recursion, but possibly too late with visible intermediate states.
