## Findings

### AUDIT-LOGIC-B2-1

- **Severity:** Critical
- **File:** `app/src/main/java/net/devemperor/dictate/state/modules/AudioModule.kt:99-110` (no-op guard) + `:228-238` (just-resolved guard); root mechanism in `app/src/main/java/net/devemperor/dictate/core/BluetoothScoManager.kt:121-126`
- **Description:** **BT-mic recording hangs forever in `Preparing(awaitingSco=true)` when SCO is already connected at recording start.** Trace: a BT-mic `StartRecording` enters `Preparing(awaitingSco=true)` with **no** `AllocateMediaRecorder`; AudioModule's observer cascades `RecordingStarted` → `Effect.StartBluetoothSco` → `BluetoothScoManager.startSco()`. If `audioManager.isBluetoothScoOn` is already `true` (back-to-back BT recordings before the SCO-disconnect broadcast lands, or another app/the system already holds SCO), `startSco` takes the early-return branch (`BluetoothScoManager.kt:122-126`): it calls `callback.onScoConnected()` **synchronously and returns `true` WITHOUT arming the 2500 ms timeout** (`postDelayed` at `:138` is never reached). `onScoConnected` emits `OnBluetoothScoStateChanged(Connected)`. But `AudioModule.reduce` (`:104` `if (newSco != state.bluetoothSco)`) finds `audio.bluetoothSco.phase` is **already `Connected`** (stale from the prior recording — `StopBluetoothSco`→`release()` does not synchronously reset the phase; the `Disconnected` broadcast is async and hasn't arrived) ⇒ reducer returns **null (Rejected)** ⇒ no state write ⇒ the observer's `justResolved` check (`:231` `prevPhase != nextPhase`) is `Connected==Connected` ⇒ **`false`** ⇒ `ScoRouteResolved` is never cascaded. `Preparing.awaitingSco` stays `true`, `AllocateMediaRecorder` never fires, and **no subsystem timeout exists to recover** (the early-return path skipped it). The recording is silently dead: no audio, no `Preparing→Active`, no §7.6 notification (it only appears on `Preparing→Active`), no error surfaced to the user.
- **Why it matters:** This is a hard hang on the exact opt-in path (BT mic) the C6-W1 repair was created to fix, and it ships only after C7 deletes the legacy fallback — so there is no safety net. The block report's BT-SCO design rationale (`reports/B2-theme-b-recording-drive.md:1102-1104` and `research/recording-audiofocus-btsco-handshake.md:74,89,115`) explicitly asserts "subsystem-owned 2500 ms timeout — no new timer needed"; that premise has a hole precisely in the already-connected branch where `startSco` returns before `postDelayed`. The "SCO unavailable (no BT device)" row of the research failure-matrix also assumes `startSco` always posts the timeout — true only on the not-yet-connected branch. Realistic trigger: user does two BT-mic dictations in a row (very common usage), or another app held SCO.
- **Suggested fix scope:** medium
- **Suggested fix:** Decouple the deferred-allocate trigger from a *phase transition*. Options (needs the repair-sub-phase to pick): (a) when `BluetoothScoManager.startSco` returns `true` (already connected), have the adapter still emit a distinct settle signal the observer acts on regardless of prior phase — e.g. `AudioModule.reduce(OnBluetoothScoStateChanged)` should not no-op when a recording `is Preparing && awaitingSco` even if the phase value is unchanged (the *recording* is awaiting resolution even though the audio phase didn't move); or (b) gate the deferred allocate on `next.recording is Preparing && awaitingSco` + `next.audio.bluetoothSco.phase ∈ {Connected,Failed}` (the *level*, not the *edge*) while keeping a separate re-fire guard keyed on `awaitingSco` (which already flips to `false` after the first `ScoRouteResolved`, so a level-trigger cannot double-fire); or (c) reset `audio.bluetoothSco.phase` to `Disconnected`/`Waiting` synchronously on `StartBluetoothSco`/`RecordingStarted` so the subsequent `Connected` is always a real transition. Option (b) is the most robust (it also fixes the "SCO connects exactly at the 2500 ms timeout" race, where a phase could momentarily settle then re-settle).

### AUDIT-LOGIC-B2-2

- **Severity:** Important
- **File:** `app/src/main/java/net/devemperor/dictate/state/modules/AudioModule.kt:165-170` + `:195-211`; interaction with `app/src/main/java/net/devemperor/dictate/state/modules/RecordingModule.kt:237-294`
- **Description:** **Audio-focus is dropped for a BT-mic recording when focus is lost during the SCO wait.** While `Preparing(awaitingSco=true)`, the focus-loss → auto-pause cascade (`AudioModule.kt:165-170`) is guarded on `next.recording.isActiveOrPaused`; `Preparing` is deliberately NOT active-or-paused (`DictateUiState.kt:204-205`), so a focus-loss during the SCO handshake does **not** pause and does **not** cascade `RecordingEnded`. `RequestAudioFocus` was already emitted once on the `Idle→Preparing` engagement edge; it is never re-requested. When `ScoRouteResolved` later drives `Preparing→Active`, that is an already-engaged→engaged transition (`isEngaged()` true on both sides) and the `Paused→Active` resume clause doesn't match, so `RecordingStarted` does **not** re-fire. Net: the recording goes Active having lost audio focus mid-Preparing with no recovery — other apps' audio keeps ducking/playing over the recording. Legacy did not have this window (it requested focus right before `MediaRecorder.start()`, after the SCO wait).
- **Why it matters:** BT-mic + an interrupting audio focus change (notification sound, navigation prompt) during the ~0–2500 ms SCO handshake is plausible; the recording proceeds without focus. Not a hang, but a silent audio-quality / behavioural regression vs. legacy on the same opt-in path as B2-1.
- **Suggested fix scope:** medium
- **Suggested fix:** Either re-request audio focus on the `Preparing(awaitingSco)→Active` (post-SCO) edge, or move the `RequestAudioFocus` emission for the BT path to fire alongside the deferred `AllocateMediaRecorder` (matching legacy's "request focus right before recorder start" timing). Needs the repair-sub-phase to choose against the §15.3 SRP constraint (focus stays AudioModule-owned).

### AUDIT-LOGIC-B2-3

- **Severity:** Important
- **File:** `app/src/main/java/net/devemperor/dictate/state/modules/RecordingModule.kt:415-431` (Active+StopRecordingAndSend) and `:479-492` (Paused+StopRecordingAndSend); IME side `DictateInputMethodService.java` `stopRecording()` (diff lines 268-305)
- **Description:** **`StopRecordingAndSend` from a non-bearing recording state silently drops the user's recording with no feedback.** The IME `stopRecording()` snapshots the R-1 config (`captureFreshConfigSnapshot`) and primes the pipeline UI (`primePipelineUiForNewPath()`) *before* dispatching `StopRecordingAndSend`. If the FSM is not `Active`/`Paused` at that instant (e.g. still `Preparing` — BT-SCO wait not yet resolved, or a slow `MediaRecorder.prepare()`), the `StopRecordingAndSend` reducer arm is absent for `Preparing`/`Idle` ⇒ `DispatchOutcome.Rejected("reducer-null")` ⇒ **no `EmitPipelineTrigger`, no pipeline**. But the IME has already: (1) consumed/reset the one-shot flags (`livePrompt=false`, `autoSwitchKeyboard=false`, `pendingLivePromptChain` armed) inside `captureFreshConfigSnapshot`; (2) shown "Sending…/progress" UI via `primePipelineUiForNewPath()` + `uiController.startPipeline(...)`; (3) cleared `newPathRecordingSessionId=null`; (4) left a `freshSnapshots` entry that will only be cleared on next process boot. The recording in `Preparing` is now orphaned (it will still go Active later but nothing will ever send it — `newPathRecordingSessionId` is null), the keyboard is stuck showing a pipeline that never starts, and the live-prompt/auto-switch state was destructively consumed. The IME's only guard checks `sessionId==null || pipelineBinder==null || resolver==null` — it does **not** check the FSM is in a sendable state. F-7 `require(isNotBlank)` does not help (the id is non-blank; the problem is the *recording state*, not the id).
- **Why it matters:** Tapping Send while still "Preparing" (BT users especially, given B2-1/B2-2 widen the Preparing window) loses the recording with a permanently-stuck "Sending…" keyboard and no error. The reducer-null is the correct *FSM* outcome, but the IME pre-commits irreversible side-effects on the assumption the dispatch will be accepted.
- **Suggested fix scope:** medium
- **Suggested fix:** Have `stopRecording()` gate on the authoritative recording state before the destructive snapshot/prime (it already has `isEffectiveRecordingActiveOrPaused()` — call it here, or capture the dispatch `DispatchOutcome` and roll back the UI prime + restore the flags on `Rejected`). Alternatively add a `Preparing+StopRecordingAndSend` reducer arm that defers the send until `MediaRecorderReady` (a "stop requested while preparing" sub-state) — larger, but matches user intent. Needs research/triage.

### AUDIT-LOGIC-B2-4

- **Severity:** Nice-to-have
- **File:** `app/src/main/java/net/devemperor/dictate/state/modules/RecordingModule.kt:358-362`
- **Description:** Defensive `?:` fallback `state.target ?: InsertionTarget.INPUT_CONNECTION` on the deferred-allocate arm. The KDoc (`:344-345`) asserts `target` is non-null exactly on the `awaitingSco` path so the `?:` "cannot fire under the FSM contract". That invariant holds for the current `StartRecording(BT)` constructor (`:259-263` sets `target = action.target`), but it is enforced only by convention, not by the type system (`Preparing.target` is `InsertionTarget? = null`). If a future caller constructs `Preparing(awaitingSco=true)` without `target`, the silent `INPUT_CONNECTION` default would mis-route insertion with no diagnostic. Per the F-7 precedent in this same file (fail-fast on the analogous `sessionId` invariant), a `requireNotNull(state.target)` on the `awaitingSco` deferred-allocate arm would make the invariant load-bearing rather than silently papered over.
- **Why it matters:** Latent correctness landmine; consistent with the file's own F-7 fail-fast philosophy. Low likelihood today (single caller).
- **Suggested fix scope:** small
- **Suggested fix:** Replace the `?:` with `requireNotNull(state.target) { "ScoRouteResolved on awaitingSco Preparing requires non-null target" }`.

### AUDIT-LOGIC-B2-5

- **Severity:** Nice-to-have
- **File:** `app/src/main/java/net/devemperor/dictate/core/AudioFocusGate.kt:45-47` vs `app/src/main/java/net/devemperor/dictate/state/modules/AudioModule.kt:127-147`
- **Description:** Audio-focus request is gated on `audioFocusEnabledPref` (`AudioModule.kt:130`) but `ReleaseAudioFocus` is emitted **unconditionally** on every `RecordingEnded` (`:141-147`), and `terminate()` (`:247-250`) also releases unconditionally. When `Pref.AudioFocus=false`, `request()` is never called but `abandon()` is — `RealAudioFocusGate.abandon()` calls `audioManager.abandonAudioFocusRequest(request)` for a request that was never made. This is **behaviourally safe** (Android `abandonAudioFocusRequest` is a harmless no-op / `AUDIOFOCUS_REQUEST_FAILED` without exception or side-effect; double-release across Stop-then-Cancel or Stop-then-`terminate()` is likewise idempotent). Flagged only as an asymmetry note: the request/release gating is not symmetric, which is non-obvious for a future maintainer reading the reducer. The KDoc at `:138-140` already documents the idempotence rationale, so this is informational.
- **Why it matters:** No functional bug; documented for completeness per the audit-prompt's explicit audio-focus-release-symmetry verdict request. Verdict: **symmetric in effect** (idempotent abandon), **asymmetric in code** (release ungated).
- **Suggested fix scope:** small (optional)
- **Suggested fix:** None required. Optionally gate `ReleaseAudioFocus` on `audioFocusEnabledPref` too for code-symmetry, but unconditional release is the safer choice if the pref flips mid-session — leave as-is and rely on the existing KDoc.

### AUDIT-LOGIC-B2-6

- **Severity:** Nice-to-have
- **File:** `app/src/main/java/net/devemperor/dictate/state/modules/RecordingModule.kt:415-431` (StopRecordingAndSend, no DismissNotification) + `app/src/main/java/net/devemperor/dictate/core/PipelineNotificationCoordinator.kt:117-132`
- **Description:** `StopRecordingAndSend` deliberately does **not** emit `DismissNotification` (seamless Recording→Pipeline hand-off; `RecordingModule.kt:206-211` KDoc). The hand-off relies on the `EmitPipelineTrigger → TriggerPipeline → PipelineModule` re-`show()`ing a `Pipeline` status on the same NOTIF_ID. If the pipeline trigger never produces a `Pipeline`-status `show()` (e.g. `ImePipelineConfigResolver.resolveFresh` throws because no snapshot — the documented R-1 fail-loud path at `ImePipelineConfigResolver.kt:147-153`, or `PipelineModule` rejects `TriggerPipeline` from a non-Idle state), the **recording-phase FGS notification (`[Pause][Stopp][Senden]`) is left on screen with no live recording behind it** — a stuck/orphan notification whose action buttons now dispatch into a dead FSM. This compounds with B2-3 (Send-from-Preparing): there `StopRecordingAndSend` is Rejected so no `EmitPipelineTrigger` at all, but if a `Recording` notification was showing it is never dismissed. The coordinator's `EffectFailure`/throw path does not dismiss either (it swallows `notify` failures, `:122-131`, but a *resolver* throw surfaces as an `Action.EffectFailure` to `PipelineModule`, not the coordinator).
- **Why it matters:** Edge-only (requires the pipeline-start to fail after a successful recording), but the failure mode is a permanently-stuck notification with live-looking but dead buttons. Worth a PipelineModule `EffectFailure`/reject arm that dismisses or repaints the notification.
- **Suggested fix scope:** medium
- **Suggested fix:** Confirm `PipelineModule`'s `SubmitPipeline`/`TriggerPipeline` failure arm emits a notification dismiss (or terminal repaint) so a failed hand-off cannot strand the recording notification. This is partly a PipelineModule (Block-other) concern — note for the consolidator to route; the RecordingModule side (no dismiss on StopRecordingAndSend) is correct *given* the pipeline always picks up.
