### AUDIT-LOGIC-B5-1

- **Severity:** Critical
- **File:** `app/src/main/java/net/devemperor/dictate/state/render/ImeViewBackend.kt:335` + `app/src/main/java/net/devemperor/dictate/state/render/SpecialTouchHandlerInstaller.kt:229-260` + `app/src/main/java/net/devemperor/dictate/keyboard/CursorSwipeTouchHandler.kt:77`
- **Description:** **SPACE tap commits TWO space characters (double-commit).** `ImeViewBackend.wireStaticHandlers` wires an `OnClickListener` for **every** button in `buttonViews` (line 335 — `buttonViews.forEach { (id, view) -> view.setOnClickListener {...} }`), including `SPACE`. The SPACE click `actionResolver` is `{ SpaceKey }` (`LayoutCatalog.kt:139/190`) → `KeyboardInputModule` → `Effect.SendSpace` → `inputConnectionProvider()?.commitText(" ", 1)`. SPACE *also* has the `buildSpaceTouchHandler` `OnTouchListener` whose `CursorSwipeTouchHandler` is constructed with `consumeTouchEvents = false` (`SpecialTouchHandlerInstaller.kt:250`). On a tap (no swipe), `CursorSwipeTouchHandler.onTouch` fires `onTap()` → `commitText(" ", 1)` (space #1) **and then returns `false`** (`CursorSwipeTouchHandler.kt:77` returns `consumeTouchEvents`). Because the touch listener returns `false`, Android's View dispatch does not consume the event and proceeds to `performClick()`, firing the SPACE `OnClickListener` → `SpaceKey` → `commitText(" ", 1)` (space #2). **Net: one physical SPACE tap → two spaces inserted.** Verified against the deleted legacy `MainButtonsController` (`git show c92ebd1:` — `grep` shows **no** `views.spaceButton.setOnClickListener`): legacy wired SPACE with a touch listener *only*; its `consumeTouchEvents=false` was harmless because there was no SPACE click handler to fall through to. The cutover (CR1 `wireStaticHandlers` click-for-all + CR4 catalog `SpaceKey`) introduced the second commit path. This is the same root cause the block-report's CR4-IMPL-4 documents but mis-classifies as "spec-mapped target / not a defect" — Spec 2 §6's "click for ALL + touch for SPACE/BACKSPACE/ENTER" only yields correct behaviour if the SPACE touch handler *consumes* the tap; `CursorSwipeTouchHandler` deliberately must return `false` (its own KDoc: so cursor-swipe MOVE events propagate), so the two paths cannot coexist as wired.
- **Why it matters:** Typing a space is the single most frequent keyboard interaction. Every space becomes a double-space silently — no crash, no log — exactly the silent-regression class Block B5 is supposed to gate against (RR-1). It survived the CR-RGATE gate because the gate is a visibility/render harness and the `ImeViewBackend` unit tests use a fake that does not model Android's touch→`performClick` fallthrough. BACKSPACE/ENTER are **not** affected (traced): `BackspaceSwipeHandler.onTouch` returns `false` on tap but has *no* delete-on-tap `onTap` of its own, so only the single click path fires; ENTER's overlay handler likewise has no commit-on-tap. The defect is SPACE-unique because `CursorSwipeTouchHandler.onTap` itself commits.
- **Suggested fix scope:** small (one-file): either (a) exclude `SPACE` from the `wireStaticHandlers` click loop the same way it's excluded from press-animation (`ImeViewBackend.kt:402-405`) so SPACE has only the touch `onTap` (legacy parity), or (b) make `buildSpaceTouchHandler` consume the tap (return `true` on ACTION_UP-tap path) while still returning `false` during swipe — but (a) is the legacy-faithful, lower-risk option.
- **Suggested fix:** Prefer (a): in `ImeViewBackend.wireStaticHandlers`, skip `view.setOnClickListener` for `SPACE` (and verify BACKSPACE/ENTER click semantics are intended — they currently do single-commit via click, matching the catalog model, so leave those). Then SPACE = touch `onTap` only = one space, legacy-identical. Add a unit/Robolectric test asserting one SPACE tap = exactly one `commitText(" ",1)`.

### AUDIT-LOGIC-B5-2

- **Severity:** Critical
- **File:** `app/src/main/java/net/devemperor/dictate/core/DictateInputMethodService.java:2144-2192` (`resolveEffectiveLanguage` / `reprocessStagingOverrideOrNull`) + `:4141-4145` (`onResendLongClicked` → `enterReprocessStaging`) + `:2378-2402` (`setLanguageFromPicker`, the sole `SetOverride` dispatch site)
- **Description:** **F-6 collapse loses the staged language for ReprocessStaging sessions where the user does not manually re-pick, and never clears the override on staging exit (stale-override leak across sessions).** The block-report's Issue Index claims "F-6 → closed CR-DEL... effective-language read collapsed to single `LanguageState.override` carrier... no regression". Trace says otherwise. (1) **Lost staged language:** `onResendLongClicked()` enters ReprocessStaging via `pipelineStepRowRenderer.enterReprocessStaging(..., lastSession.getLanguage())` — this sets only the View-side `PipelineUiState.ReprocessStaging.selectedLanguage`; it does **not** dispatch `LanguageAction.SetOverride(lastSession.getLanguage())`. The *only* `SetOverride` dispatch in the entire `app/src/main/` tree is `setLanguageFromPicker():2392`, fired exclusively when the user explicitly opens the language picker and chooses during staging. So if the user enters staging for a session recorded in (e.g.) French and presses record *without* re-picking, `resolveEffectiveLanguage()` → `reprocessStagingOverrideOrNull()` reads `LanguageState.override` (null/stale, never set for this session) → falls through to the permanent pref language. Under the pre-collapse dual-carrier, `resolveEffectiveLanguage()` read `ReprocessStaging.selectedLanguage` = the session language. **The language chip + transcription-config snapshot now show the wrong (permanent) language during such a staging session.** (Note: the actual reprocess *job* is unaffected — `handleReprocessSend():4223` reads `staging.getSelectedLanguage()` directly off the View-side carrier — so this is a display/config-read fidelity regression, not a wrong-transcription bug, but it is user-visible and contradicts "no regression".) (2) **Stale-override leak:** the KDoc at `:2133` asserts `LanguageState.override` is "cleared on staging exit". There is **no `SetOverride(null)` / clear dispatch anywhere in `app/src/main/`** (`grep -rn SetOverride app/src/main/` → only `:2392`). `cancelReprocessStaging()` (`:4200`) and the reprocess-send completion do not dispatch a clear. So: enter staging A, pick "de" → `override="de"`; exit; enter staging B (session recorded "en") without re-picking → `reprocessStagingOrNull()` is true (renderer in staging B) → `reprocessStagingOverrideOrNull()` returns the stale `"de"` → chip shows "de" for an "en" session. The `reprocessStagingOrNull()` guard prevents the stale value leaking *outside* staging but does nothing to prevent it leaking *between* staging sessions. The KDoc invariant is false and masks the bug.
- **Why it matters:** F-6 is explicitly called out as a load-bearing CR-DEL deliverable ("F-6 → closed CR-DEL"). The collapse is incomplete: it removed the read side of the dual-carrier without wiring the write side (`SetOverride` on staging entry from the session language) or the lifecycle clear (`SetOverride(null)` on staging exit). The KDoc claims an invariant the code does not implement, so a future reader trusting the doc will not catch it.
- **Suggested fix scope:** medium (two call-sites in the IME, clear pattern): on staging entry (`onResendLongClicked` mainHandler.post, alongside `enterReprocessStaging`) dispatch `LanguageAction.SetOverride(lastSession.getLanguage())` (guarded `pipelineBinder != null`, and only when the session language is non-blank — preserve the F-3 blank-guard semantics); on staging exit (`cancelReprocessStaging` path + reprocess-send transition to Preparing/Idle) dispatch `LanguageAction.SetOverride(null)`. Also correct or remove the `:2133` "cleared on staging exit" KDoc so doc ↔ code agree. Verify against the legacy `KeyboardUiController` `enterReprocessStaging` semantics (`git show c92ebd1:`) that the session-language seeding is the intended initial override.
- **Suggested fix:** needs the orchestrator/repair-agent to decide entry-seed vs. read-fallback. Lowest-risk + closest to legacy parity: seed `SetOverride(sessionLanguage)` on entry + `SetOverride(null)` on every staging exit. (Alternative — re-introduce a session-language fallback in `reprocessStagingOverrideOrNull()` reading the renderer's `selectedLanguage` when `LanguageState.override` is null — but that partially re-introduces the dual-carrier F-6 was meant to collapse, so the entry-seed/exit-clear approach is preferred and is genuinely single-carrier.)

### AUDIT-LOGIC-B5-3

- **Severity:** Important
- **File:** `app/src/main/java/net/devemperor/dictate/core/DictateInputMethodService.java:679-1088` (`onCreateInputView`) + `:1103-1109` (`attachImeViewBackendIfReady` early-return) + `:1852-1940` (`rewireCallbacks`) — the pre-bind / unbound boot path
- **Description:** **Pre-service-bind (and on bind-failure) there is no listener owner for the 9 main buttons + edit-bar + emoji + special-touch axes — the keyboard renders but is functionally inert until `onServiceConnected` fires.** CR-DEL deleted `MainButtonsController` *and* its `registerAllListeners()` unbound fallback. `attachImeViewBackendIfReady` returns early when `pipelineBinder == null` (`:1104-1108`) so `ImeViewBackend` / `SpecialTouchHandlerInstaller` / `EditBarController` / `EmojiController` / `OverlayCharactersController` are **not** constructed/attached and the visibility gates are not armed. Confirmed by grep: the only listeners wired pre-bind are the info-bar / overlay-permission / promptTrash buttons (`:817/:833/:911`); RECORD/RESEND/BACKSPACE/SPACE/ENTER/TRASH/PAUSE/AUDIO_FOCUS + all edit-bar/emoji buttons have **zero** click/long-press/touch listeners while unbound. The view itself is not blank (the layout XML's static `android:visibility` defaults render the main button row), so the user sees a normal-looking keyboard whose buttons silently do nothing. Mitigation present: `onServiceConnected` re-runs `attachImeViewBackendIfReady` (`:463-467`) and `KeyboardLayoutManager.attachBackend` synchronously renders the current state snapshot to the freshly attached backend (`KeyboardLayoutManager.kt:99-103`), so the window self-closes once the same-process binder arrives (`bindService` is issued in `onCreateInputView`; same-process bind is near-instant). The block-report documents this as accepted ("the keyboard always binds while open... brief pre-bind window... the §6.1 staged-safety-net surface collapsing at the point-of-no-return"). The residual logic risk: if `bindService` returns false (`:698-702` — package-manager failure / permission), `pipelineServiceBindAttempted` is reset but nothing re-triggers a bind until the *next* `onCreateInputView`; until then the keyboard is permanently inert with no user-visible error.
- **Why it matters:** This is the load-bearing "no owner drives the keyboard" question. In the common case it is a sub-second self-healing window (acceptable, as documented). The genuine gap is the bind-*failure* path: no retry/observability, the keyboard is silently dead. The legacy `MainButtonsController` unbound fallback used to make the keyboard fully functional with no service at all; CR-DEL removed that safety net and the only remaining recovery is an implicit "next view-recreate" — which may not happen if the user keeps the keyboard open. This is the point-of-no-return tradeoff the spec authorised, but the bind-failure sub-case is not covered by the "binds near-instantly" reasoning.
- **Suggested fix scope:** medium — out of pure CR-DEL deletion scope but a real post-cutover robustness gap. Options: a bounded `mainHandler.postDelayed` re-bind retry on `bindService`-false, and/or a user-visible "service unavailable" info-bar so an inert keyboard is not silent. Recommend the orchestrator route this to triage rather than inline-fix (it is an architecture/robustness decision, not a mechanical correction).
- **Suggested fix:** needs research/decision (re-bind retry policy + user surface). Document the accepted pre-bind window vs. the unhandled bind-failure case explicitly.

Trace: RESEND click → `imeSideAffordance(RESEND,false)` (IME re-checks `pipelineBinder.getState()...getResendCooldown()`; runs `onResendClicked()` only if not in cooldown) → then catalog `actionResolver` dispatches `ResendLastAudio` → `ResendModule` synchronously sets `resendCooldown=true` (`DictateOrchestrator.dispatch` is a synchronous CAS-loop `MutableStateFlow.update`, not async). `onResendClicked()` schedules the CR4-IMPL-2 `ResendCooldownExpired` postDelayed-dispatch (`:3973-3981`, `pipelineBinder`-guarded, idempotent — `ResendModule.kt:97` no-ops when already false), so the cooldown cannot latch forever.
