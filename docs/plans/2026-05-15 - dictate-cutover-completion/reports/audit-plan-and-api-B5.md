## Findings

### AUDIT-PLAN-AND-API-B5-1

- **Severity:** Important
- **File:** `app/src/main/java/net/devemperor/dictate/state/render/EditBarController.kt` (missing `refreshAudioFocusIcon`); `app/src/main/java/net/devemperor/dictate/core/DictateInputMethodService.java:4470-4478` (the incorrect "owns every axis" claim); legacy proof `git show c92ebd1:.../MainButtonsController.kt:368-385`
- **Description:** The deleted `MainButtonsController.refreshAudioFocusIcon(enabled)` set the icon **foreground + contentDescription on BOTH** the main-button-area `audioFocusButton` **and** the edit-bar `editAudioFocusButton` (legacy lines 383–384). Post-CR-DEL, only the **main-button-area** AUDIO_FOCUS slot icon is state-driven (catalog `iconResolver` → `resolveAudioFocusIconForSlot`). **No code anywhere mutates `editAudioFocusButton.foreground` or its `contentDescription`** (`grep` for any edit-audio-focus icon/foreground/contentDescription write = empty; `EditBarController` wires only the click listener + theme color). The edit-bar `edit_audio_focus_btn` is therefore frozen at its static layout default `android:foreground="@drawable/ic_baseline_volume_off_24"` (`activity_dictate_keyboard_view.xml:419`) and never reflects the actual audio-focus enabled/disabled state, and TalkBack never announces the state phrase. The RR-3 per-class responsibility-trace (B5 report, CR-DEL §"Step 1") marked `refreshAudioFocusIcon → AUDIO_FOCUS iconResolver (state-reactive)` as "✅ ported", but that resolver only owns the main-button-area twin — the edit-bar twin is a stranded responsibility (the trace conflated the two sites legacy code drove together). Spec 2 §13.2 F-4 (`2-keyboard-layout.reviewed.md:2447/2474/2475`) explicitly prescribes `EditBarController.refreshAudioFocusIcon` calling the **shared `resolveAudioFocusIcon` SSOT** so both sites listen to the same StateFlow and map through the same function — this F-4 contract was not implemented when `EditBarController` was extracted in CR-EXTRACT. Structurally this is the same "§13.2-assumed-an-owner-method-never-created" anti-pattern as CR4-IMPL-1, recurring at the edit-bar audio-focus *icon* axis (it slipped through because §3's 16-group map G14 enumerated only the main-button-area `refreshAudioFocusIcon`, not the edit-bar twin that the same legacy method drove).
- **Why it matters:** User-visible behaviour regression on the always-visible edit bar: the audio-focus button icon no longer toggles `volume_off`↔`volume_up`, so the user cannot tell from the edit bar whether audio-focus is active, and the accessibility contentDescription is permanently wrong. This is a parity violation against AC-RR-1..5 (per-group behaviour parity, "no user-visible regression") and a missed Spec 2 §13.2 F-4 contract. It is the exact silent-blank/stale-UI class of regression the Theme C-R staged-safety-net exists to prevent.
- **Suggested fix scope:** small (one new method + one IME wiring point) — medium if the F-4 StateFlow-shared SSOT path is wired fully per spec.
- **Suggested fix:** Add `EditBarController.refreshAudioFocusIcon(enabled: Boolean)` (or an `applyAudioFocusIcon`) that sets `editAudioFocusButton.foreground` + `contentDescription` via the existing shared `resolveAudioFocusIcon(enabled)` SSOT helper (`state/layout/IconResolvers.kt:59`) — byte-equivalent to the deleted legacy lines 368–385 — and drive it from the IME on the same `state.audio.audioFocusEnabledPref` reactive path the AUDIO_FOCUS slot uses (the F-4-prescribed shared-StateFlow model), or minimally call it from the existing audio-focus-toggle handler + initial render. Update the IME `:4470-4478` comment (it currently incorrectly asserts the iconResolver "own[s] every axis").
